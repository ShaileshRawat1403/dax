# DAX Positioning

This guide explains how DAX should be framed as a product.

## One-Line Positioning

**DAX is the governed execution workstation for AI-driven software work, giving teams approvals, replayability, and audit-grade control instead of black-box agent behavior.**

## Short Version

DAX is not trying to be the most conversational AI coding tool.

DAX is trying to be the most trustworthy system for running AI work in a real repository when the work needs:

- explicit approval points
- visible planned changes
- durable run history
- operator review
- recovery after interruption

## Product Category

The strongest category for DAX is:

> **Governed execution workstation**

That is stronger than:

- coding assistant
- AI IDE
- terminal agent
- prompt wrapper

Because it explains why DAX exists even when teams already have those tools.

## Comparison

| Tool | Core mental model | Strength | Where DAX differs |
| :--- | :--- | :--- | :--- |
| **Cursor** | AI-native coding IDE | Fast in-editor code generation and editing | DAX is more about approvals, reviewability, and run governance than editor convenience |
| **Codex** | Agentic coding runtime | High implementation throughput and strong code execution | DAX treats the run as a governed object with explicit intervention and replay surfaces |
| **Claude Code** | Terminal-native coding agent | Strong repo understanding and CLI execution flow | DAX is more operator-first, with speculative previews, approval objects, and recovery semantics |
| **DAX** | Governed execution workstation | Control plane for AI work in real repositories | Optimized for trust, evidence, and delivery discipline |

## What DAX Should Win On

DAX should win on:

- operator trust
- approval clarity
- diff-before-write review
- audit trail quality
- recovery and resumability
- release-readiness workflows

DAX does not need to win on:

- the flashiest autocomplete
- the least opinionated UX
- the lowest-friction freeform chat loop

## Product Message

When describing DAX publicly, bias toward this structure:

1. **What it is**
   DAX is a governed execution workstation for AI-driven software work.
2. **Why it exists**
   Teams need control, traceability, and reviewable delivery, not just agent speed.
3. **How it works**
   Intent becomes a run. The run becomes a planned, governed, replayable execution trail.
4. **Where it wins**
   Approvals, speculative diffs, operator review, recovery, and audit-grade visibility.

## Messaging Guardrails

Avoid positioning DAX as:

- “just another AI coding assistant”
- “an autonomous agent that happens to ask nicely”
- “chat with governance bolted on”

Prefer wording like:

- governed execution
- operator workstation
- reviewable runs
- approval-aware delivery
- evidence-forward AI operations
